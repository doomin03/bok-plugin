# Prepare an owner review, not a site
Read ../bok-report-publishing/SKILL.md and references/fidelity-contract.md there.
Use the extraction procedure in ../bol-start/SKILL.md, then STOP before implementation.
Resolve scripts in ../bok-report-publishing/scripts when installed, otherwise ../../scripts.
First read the owner's comparison target configuration: explicitly supplied path, then <repo>/docs/<report>/comparison-targets.json, then <repo>/docs/comparison-targets.json (first existing file wins; invalid selected files are errors, not fallback). Follow ../bok-report-publishing/references/image-comparison.md. The owner supplies existing project paths, sourcePaths and descriptions; the agent discovers individual chart mappings within that scope. Do not assume the current project or a previous branch is the comparison target. If configuration is absent, continue source extraction but report target comparison as blocked and request the missing owner paths/descriptions.
For each configured existing project, inspect the specified sourcePaths and description. Resolve the requested ref to an immutable commit, or record HEAD plus worktree changes if ref is omitted. Inspect via git show; do not modify the donor or switch its checkout. Non-Git projects use source file hashes and explicit unavailable commit status. Ensure preview captures correspond to the inspected source version; otherwise mark image comparison pending.
Read ../bok-chart/references/monetary-policy-patterns.md for the inspected repository patterns.
Create a unit-plan.json: one unit per body/notes/chart/table/image, with slug, kind, title, section, files, sourceRefs and acceptance.
Read ../bok-report-publishing/references/notes-and-responsive-verification.md. Reconcile document.json inlineParagraphs/noteLinks with the rendered document's visible numbering and create note-map.json; do not use internal note IDs as display numbers. Add note click/content parity and mobile/tablet/PC chart/table checks to each applicable unit's acceptance. Older schema-2 source packages lack inline note positions: rerun extraction with schema 3, preserving the old package.
For chart units also record strategy (reuse/new/undecided), baseline {branch,commit,files}, comparison (series/type/axes/units/period/annotations/responsive differences), sourceEvidence (repo-relative evidence files), and questions.
AI judges similarity first, the human decides after. For each chart, inspect candidates only in the owner-configured project/sourcePaths. When a configured project uses the supported BOK graphData layout, run scripts/match-chart-data.py --repo <configured-project> --source <extracted-source> --out <matches.json>, retaining only candidates within configured sourcePaths and verifying the inspected ref. This helper reads the working tree and is not ref-aware; do not use its output as evidence for another ref. For other layouts inspect source/data directly and record unsupported automated matching without inventing scores. Record a `similarity` field with target ID, exact donor source, commit/hash, series/shape/period/unit assessment, confidence and proposed strategy. workflow.mjs prepare renders it above the empty owner decision.
A visually similar picture or historical numeric match alone does not prove reuse suitability; the exact matcher and your similarity note are inputs to the owner, never an approval.
Keep source images under OpenSpec evidence, never public assets or a chart fallback. Distinguish genuine photos/diagrams from statistical charts.
On Windows render a comparison with scripts/render-comparison.ps1 -Repo <repo> -Change <change-id> -SourceImage <extracted image>. It only writes under the change's evidence/source-images. Link that PNG in owner-review.md, not in Vue.
For every chart/image unit, follow ../bok-report-publishing/references/image-comparison.md: compare the report source with a capture of the owner-configured existing source, write per-item analysis, and run compare-images.py --targets <selected-config> to generate comparison.html, review.md and metrics.json in a new evidence directory. Record targetId and targetSource for each selected candidate. No suitable source candidate means a pending entry in owner-review.md, not a fabricated mapping. Missing candidate screenshots remain pending in the generated artifacts. Save the target config snapshot and inspected source/commit evidence under the change and include them in unit-plan sourceEvidence before workflow prepare. Link all artifacts in owner-review.md; numeric pixel similarity never grants reuse approval.
After finalizing comparison evidence and the plan, run workflow.mjs prepare --repo <repo> --plan <plan>, then link the generated comparison artifacts in owner-review.md.
The generated comparison.html is the interactive owner-review UI: each chart shows the source figure beside the owner-configured existing chart, with per-chart 판정 buttons 동일함/유사함/다름/보류 (reuse/reuse-adapt/new/hold) and a 검토 의견 field. The owner clicks 판정 and writes a comment; 적용·저장 (and CSV 저장·연결) persist to comparison-review.csv via the browser File System Access API and localStorage, no server required. Present this page to the owner as the primary review surface; bok-spec then reads comparison-review.csv to build decisions.
Present owner-review.md with source image links, configured donor source/preview, differences, proposal and open questions. Owner can edit the review or reply in chat.
The next command is bok-spec. Start never approves its own proposal, registers Jira, or implements any unit.
